# DECISIONS.md

Lightweight architecture decision records for Video Factory. `PHASES.md`
is the execution authority; this file records decisions made while
executing it, especially ones not fully specified by the plan itself.

---

## ADR-001: Standalone git repository, isolated from an unrelated parent workspace

**Date:** 2026-10-09
**Status:** Accepted

**Context:** This project's working directory was initially located beneath an unrelated
parent workspace containing unrelated material.
PHASES.md requires this project to become its own public GitHub repository
with clean, phase-based commit history and strict secret/PII hygiene.

**Decision:** Run `git init` inside the project directory itself. This
project's history is fully independent of the parent workspace.

**Consequence:** Phase commits here never touch or risk exposing anything
from the parent workspace.

## ADR-003: One `domain` package for core data contracts; small per-concern packages for behavior

**Date:** 2026-10-09
**Status:** Accepted

**Context:** PHASES.md section 5 lists all core data types together under
one "Core Domain Model" heading. PHASES.md section 19 separately asks for
small, capability-specific interfaces rather than one large interface.

**Decision:**
- All pure data contracts from section 5 live in `domain`.
- Behavioral interfaces that consume `domain` types live in their own
  small packages: `provider`, `decision`, `resource`, `event`.

**Consequence:** No duplicate/divergent type definitions across packages;
no "god interface"; package-qualified names stay idiomatic
(`provider.Provider`, not `provider.ProviderProvider`).

See `ARCHITECTURE.md` for the full rationale.

## ADR-004: Open string vocabularies instead of closed enums for categories/capabilities

**Date:** 2026-10-09
**Status:** Accepted

**Context:** PHASES.md repeatedly requires provider/model/flow/framing
independence (sections 4.1, 4.2, 7) and explicitly says shot categories in
section 6 are "recommended," not exhaustive.

**Decision:** `ShotCategory`, `PrimitiveType`, `AssetKind`, and capability
tags (`ProviderCapabilities.Tags`, `ModelCapabilities.Tags`) are typed
strings with exported constants for the known/recommended values, not
closed Go enums (`iota`-based types restricted to a fixed set).

**Consequence:** Later phases/providers can introduce new categories,
primitives, or capability tags without modifying `domain`. The tradeoff is
weaker compile-time exhaustiveness checking, which is acceptable given the
explicit pluggability requirement.

## ADR-006: `decision.Policy` included in Phase 00 as a pure value type, not a decision engine

**Date:** 2026-10-09
**Status:** Accepted

**Context:** PHASES.md section 8 gives a concrete, deterministic threshold
example (`score >= 0.85 -> YES`, `score <= 0.30 -> NO`, otherwise
`UNCERTAIN`) as part of describing decision *contracts*. Phase 06 owns the
full Decision Engine (provider registry, fallback/escalation policy).

**Decision:** Phase 00 includes `decision.Policy` / `decision.Evaluate` as
a small, pure, provider-agnostic value type satisfying the "decision
contracts" TODO item, without implementing provider routing, registries,
or escalation — that scope stays in Phase 06.

**Amendment (same date, prompted by Phase 00 review #1/#2):** `Evaluate`
alone silently accepted inverted/out-of-range/non-finite thresholds
(e.g. `YesThreshold < NoThreshold`), producing a plausible-looking but
wrong verdict instead of a detectable error. Added `Policy.Validate()
error`, which callers constructing a `Policy` from configuration must
call; `Evaluate` itself remains a pure, side-effect-free function and
still does not validate (so it stays trivially composable), but its doc
comment now says so explicitly.

## ADR-007: Duration/timing serialization and relativity conventions

**Date:** 2026-10-09
**Status:** Accepted
**Prompted by:** Phase 00 review #1 (terra) and #2 (astra) — both flagged
undocumented duration units and ambiguous timing relativity.

**Context:** `domain` has two different kinds of time values: positions
on the video timeline (`Shot.Duration`, `TimelineEntry.Start/End`,
`VisualElement.Start/End`, `ReviewFeedback.Timestamp`) and real-world
operation timings (`GenerationResult.DurationMs`). Left undocumented,
`time.Duration`'s default JSON encoding (integer nanoseconds) and the
relativity of each timestamp (shot-relative vs. project-relative) were
ambiguous across packages.

**Decision:**
- Video-timeline positions use `time.Duration`, serialized by
  `encoding/json` as integer nanoseconds.
- Real-world operation timings use explicit `...Ms int64` fields
  (`GenerationResult.DurationMs`) instead, since they cross future
  process/worker boundaries where millisecond precision is sufficient
  and an explicit field name avoids re-deriving units.
- `TimelineEntry.Start`/`End` are project-timeline-relative.
- `VisualElement.Start`/`End` are shot-relative (0 = start of the shot
  named by `ShotID`), matching the per-shot `RenderManifest` convention.
- `ReviewFeedback.Timestamp` is shot-relative when `ShotID` is set,
  otherwise project-relative.
- All intervals are end-exclusive: `[Start, End)`.
- `Bounds` are normalized `[0,1]` coordinates, origin top-left.

These conventions are recorded as doc comments on the relevant types in
`domain/timeline.go`, `domain/visual.go`, and `domain/review.go`, and
exercised by `domain/domain_test.go`.

## ADR-008: `map[string]any` extension fields use plain JSON values; no schema in Phase 00

**Date:** 2026-10-09
**Status:** Accepted
**Prompted by:** Phase 00 review #2 (astra) — flagged that
`Properties`/`Payload`/`Input`/`Metadata` fields have no defined,
lossless JSON contract (e.g. large integers losing precision through
`float64`).

**Context:** Several contracts (`Primitive.Properties`,
`Change.Payload`, `DecisionRequest.Input`, `Asset.Metadata`, event
`Payload`) use `map[string]any` for open-ended extension data.
`encoding/json` decodes all JSON numbers in `any` fields as `float64`,
which loses precision for integers outside `float64`'s exact range.

**Decision:** For Phase 00, these fields are documented as holding
JSON-compatible values only, with the standard `encoding/json`
`float64`-for-numbers decoding behavior as the accepted default. No
schema validation or alternate numeric decoding (`json.Number`,
`UseNumber`, typed payloads) is introduced yet.

**Consequence / follow-up:** If a later phase needs lossless large
integers or typed payload validation (e.g. the Phase 02 event-worker
protocol, or Phase 13 ChangeSet mutation semantics), it must introduce
that handling explicitly at that boundary; callers should not assume
exact integer precision through these fields today.

## ADR-009: ULID IDs via a dedicated `idgen` package; path-traversal guard in `FileStore`

**Date:** 2026-10-09
**Status:** Accepted (encoding corrected same day after Phase 01 review)

**Context:** Phase 00 ADR-005 deferred ID generation strategy to
Phase 01. Phase 01 also introduces the first real persistence code
(`project.FileStore`), which derives filenames from `domain.Project.ID`.

**Decision:**
- IDs are generated by a new, dependency-free `idgen` package as
  standard ULIDs (https://github.com/ulid/spec): 48-bit millisecond
  timestamp + 80 bits of `crypto/rand` randomness, encoded as 26
  characters of Crockford Base32 with the spec's 2 leading zero padding
  bits. This keeps IDs sortable by creation time, collision-resistant,
  stdlib-only (PHASES.md section 4.9), and interoperable with standard
  ULID decoders.
  - **Correction (same-day Phase 01 review):** the first implementation
    padded the *end* of the bitstream with zeros instead of prepending
    2 padding bits before the data, as the ULID spec requires. This
    produced IDs that were internally sortable and unique but not
    decodable by a standard ULID library (e.g. the first character
    could be any of `0`-`Z`, not just `0`-`7`). Fixed in `idgen.encode`;
    pinned with `TestEncodeKnownVector` and
    `TestNewFirstCharacterIsWithinULIDRange` so it can't silently drift
    again.
  - A failed read from the OS CSPRNG is treated as fatal and surfaced
    (`newAt` returns an error; `New` panics), not silently replaced with
    a predictable/zero fallback — the original design's "fall back to
    zero randomness" rationale was wrong: a failure in the same
    millisecond would make a collision *certain*, not "extremely
    unlikely." The random source is an injectable package variable
    (`randReader`) solely so this failure path has a test
    (`TestNewPropagatesEntropyFailure`).
- `idgen.New()` is the module-wide ID-minting authority; any package may
  call it directly. `project.NewID()` is only a thin convenience wrapper
  used by this package's own constructors, not a required indirection
  for unrelated packages.
- Because a `domain.Project.ID` is, in principle, caller-supplied data,
  `project.FileStore` validates every ID against a conservative
  allow-list (`^[A-Za-z0-9_-]+$`) before deriving a filename from it,
  rejecting path separators and `..` segments. This is a defense-in-depth
  measure: today's only ID source (`idgen`) already produces safe
  strings, but a future caller/API (e.g. a Phase 12 TUI command, or a
  Phase 05 Director-provided ID) might not.

**Consequence:** `FileStore.Load`/`Save` return an error instead of
reading/writing outside the intended store directory for any ID shaped
like a path-traversal attempt. Generated IDs are genuine ULIDs usable
with any standard ULID tooling.

## ADR-010: `domain.Project` owns `Timeline` and `Assets`, not just `Plan`

**Date:** 2026-10-09
**Status:** Accepted
**Prompted by:** Phase 01 review #1 (sol, BLOCKER) and #2 (luna6, HIGH)
— both independently identified that the persisted `Project` aggregate
excluded `Timeline` and `Asset` state, so saving/loading a project
silently discarded any timeline or assets built in memory, contradicting
the phase's own name ("Project State / Timeline") and Required Result.

**Context:** Phase 00 modeled `Project`, `VideoPlan`, `Timeline`, and
`Asset` as related but structurally separate types (`Timeline` carries
its own ID and a `ProjectID` back-reference; `Asset` carries only its
own ID and media metadata, with no back-reference — it was always meant
to be owned by whatever contains it). `Project` itself only embedded
`*VideoPlan`, so `project.FileStore`, which persisted exactly one
`domain.Project` value, never saved anything not reachable from that
value.

**Decision:** Add `Timeline *domain.Timeline` and `Assets []domain.Asset`
fields to `domain.Project`, following the same optional-pointer pattern
already used for `Plan`. `project.Validate` now also validates the
embedded `Timeline` (ID, `ProjectID` linkage, and `ValidateTimeline`
against the plan's shots, including that every `VisualElement`'s shot is
actually placed on the timeline) and the embedded `Assets` (ID
uniqueness, required `Kind`/`URI`) as part of validating a `Project`.

**Consequence:** A `Project`'s plan, timeline, and assets now round-trip
through `Marshal`/`Unmarshal`/`FileStore` together, as one consistency
boundary, matching "a project can be created, loaded, modified, saved,
and validated" (PHASES.md Phase 01 Required Result). `domain.Timeline`
keeps its own ID and `ProjectID` back-reference so it remains
independently meaningful (e.g. for a future API that returns just a
timeline); `domain.Asset` is owned purely through `Project.Assets`. Both
are no longer orphaned by persistence.

## ADR-011: Typed sentinel errors and identity verification in `FileStore`

**Date:** 2026-10-09
**Status:** Accepted
**Prompted by:** Phase 01 review #1 (sol) and #2 (luna6) — both flagged
that `Load` never checked the decoded project's ID against the requested
ID, and that corrupt-data/invalid-project failures were only
string-wrapped, not classifiable with `errors.Is`.

**Decision:**
- Added `ErrCorrupt`, `ErrInvalid`, and `ErrIdentityMismatch` sentinel
  errors (alongside the existing `ErrNotFound` and
  `ErrUnsupportedSchemaVersion`), all wrapped with Go 1.20+'s
  multi-`%w` `fmt.Errorf` so `errors.Is` works alongside a human-readable
  message and the underlying cause.
- `FileStore.Load` now rejects a file whose decoded `Project.ID` does
  not equal the requested ID (`ErrIdentityMismatch`), so a copied,
  renamed, or hand-edited file cannot cause `Load(A)` to silently return
  project `B`.
- `FileStore.Save`/`Load` now document their concurrency contract
  explicitly on the `Store` interface: safe for concurrent use across
  distinct IDs; same-ID concurrent `Save`s are last-writer-wins with no
  built-in optimistic-concurrency check (callers needing conflict
  detection must build it on top, e.g. comparing `UpdatedAt`).
- `FileStore.Save`'s atomic write was strengthened: the temp file is
  `fsync`'d before `Close`/`Rename` (not just written), and the store
  directory is best-effort `fsync`'d after the rename (ignored if the
  underlying filesystem doesn't support directory `fsync`, since the
  rename itself already made the write visible).

**Consequence:** Callers can use `errors.Is(err, project.ErrInvalid)`
etc. instead of string matching. `Load` cannot return a project under
the wrong identity. Save durability is closer to "survives a crash
immediately after Save returns," not just "atomic from a concurrent
reader's point of view."

## ADR-012: Second Phase 01 review round — timeline/element placement, asset validation, flow/framing presence

**Date:** 2026-10-09
**Status:** Accepted
**Prompted by:** a confirmation re-review from the same two reviewers
(sol, luna6) after ADR-009/010/011 landed. Both independently found
further gaps the first round of fixes didn't cover.

**Decision:**
- `ValidateTimeline` now requires every `VisualElement`'s shot to
  actually have a `TimelineEntry` (not merely be a *known* shot).
  Without this, an element could pass validation while being
  unreachable from `EntryForShot`/`AbsoluteStart`, breaking the
  element-to-shot/timeline relationship (PHASES.md section 4.6.1).
- `ValidateTimeline` now requires a `TimelineEntry`'s placed duration
  (`End - Start`) to equal its shot's declared `Duration` exactly —
  the data model has no separate trim/retiming concept yet, so letting
  the two disagree would leave two conflicting "true" durations for the
  same shot.
- `Validate` now validates `Project.Assets`: non-empty, unique IDs, and
  required `Kind`/`URI`.
- `validatePlan` now requires non-empty `VideoPlan.FlowID` and
  `FramingID`. This checks only that *a* reference is present, not that
  it resolves against a registry (registries are Phase 04 scope).
- `BuildDependencyGraph` now deduplicates repeated dependency edges on
  the forward (`dependsOn`) side too, matching the dedup already applied
  to the reverse (`dependents`) side.
- `FileStore.Load` re-checks `ctx.Err()` immediately after reading the
  file (in addition to the entry check), so a cancellation that occurs
  during the read is observed before doing any further work.
- Fixed a stale test comment/assertion in `idgen_test.go`: with standard
  ULID padding, the first **10** characters (not 9) are purely
  timestamp-derived (48 timestamp bits + 2 padding bits = 50 bits = 10
  Base32 characters exactly), so two IDs minted in the same millisecond
  must share all 10, not 9.
- Corrected ADR-010's wording: `domain.Asset` has no `ProjectID`
  back-reference (only `domain.Timeline` does); `Asset` is owned purely
  through `Project.Assets`.

**Consequence:** The remaining gaps identified in the confirmation
review are closed; both reviewers' structural-validation and
documentation-accuracy concerns are addressed without expanding scope
into registry validation (Phase 04) or non-recursive graph traversal
(left as a documented, accepted limitation for Phase 01's trusted-input
scope).
